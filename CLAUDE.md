## Project Overview
InternTrack is a capstone OJT/internship monitoring system for Mater Dei College (Bohol, Philippines), built by a 4-person team (Group 1). It digitizes SIPP internship processes: student profiles, attendance/clock-in, weekly activity journals, evaluations, and reporting.

This is a **monorepo** with three parts:
- **repo root** — Laravel 13 REST API (PHP 8.3, MySQL/SQLite). There is no `api/` subfolder — the Laravel app lives at the top level (`app/`, `routes/`, `database/`, etc.)
- `web/` — Vue 3 SPA (Vite, Tailwind CSS v4, **TypeScript** — `.ts` files, `tsconfig.json`, and the `typescript` package are already in use under `web/src`)
- `mobile/` — React Native / Expo app (Expo SDK 56, TypeScript, expo-router). Currently just the default Expo template scaffolding — deferred until Phase 7, do not wire real auth/endpoints into it yet unless asked. It has its own `mobile/CLAUDE.md` (imports `mobile/AGENTS.md`) with an Expo-SDK-56-specific instruction to check the versioned docs at `docs.expo.dev/versions/v56.0.0/` before writing any mobile code — read it once mobile work actually starts

## Tech Stack (do not change without asking)
- Laravel 13, PHP 8.3, MySQL (SQLite for local/testing)
- Auth: Laravel Breeze + Sanctum — **cookie/session-based** for the web SPA (`EnsureFrontendRequestsAreStateful`); token-based auth for mobile is DEFERRED to Phase 7. **Login is USERNAME-based** (email is parked for future use): `users.username` is NOT NULL + unique; `users.email` is now **nullable** (unique-when-present). `LoginRequest` normalizes any of `login`/`username`/`email` into one identifier and resolves it against `username` OR `email` (via `filter_var` email detection), so username-only accounts and legacy email/demo accounts both sign in. It never creates accounts and only signs in an account whose email Google itself verified. **Username + password remains the primary, always-available path**; Google is purely additive, and email/password login (i.e. logging in by typing an email address) is still resolved by `LoginRequest` exactly as before.

## Hard Rules
1. **Do not create a duplicate migration.** Before creating any migration, check `database/migrations/` for whether a table/column change already exists. If a migration for that table exists and hasn't shipped, EDIT it instead of adding a new one.
2. **Do not add a second middleware layer or restructure app architecture** without explicitly proposing it first and waiting for approval.
3. **Stay on the finalized schema** (InternTrack_Database_Schema_v2, 20 tables). Do not rename tables/columns or add tables without asking. Key structural decisions already made:
   - `weekly_activity_logs` is split into a header table + `weekly_activity_log_entries` (mirrors the physical SIPP form) — same pattern for the separate `weekly_logs`/`weekly_log_entries` and `journal_entries`
   - Separate `programs`, `departments`, `student_profiles`, `journal_templates`, `system_settings` tables exist
   - `programs` has a composite unique constraint on `(department_id, cod e)` — departments are independent top-level units (e.g. CABM-B and CABM-H are two separate departments, not sub-units of one "CABM"); don't introduce a department→division→program hierarchy without confirming first
4. **Out of scope — do not build:** geofence clock-in, rotating QR clock-in, photo capture on clock-in, exit interview report generation.
5. **Record every change in CLAUDE.md as part of finishing the task, not as an afterthought.** Any new feature, schema change, bug fix worth remembering, or behavior change must get a corresponding bullet added (matching the existing section's style) or an existing stale statement corrected — before reporting the task complete, not after being asked. A change that isn't reflected here is invisible to the next session.
6. **Never `git commit`, `git push`, create a branch, or open a PR without the project owner's explicit permission for that specific action.** Approval to make a change is NOT approval to commit it. Finish the work, report what changed, and wait to be asked. This supersedes any earlier "auto-commit to main is the default" convention. It applies to the `deploy` branch above all — `docker/entrypoint.sh` runs `migrate --force` on every boot, so an unrequested push reaches live data on the next wake.


## Domain Facts
- 3 departments, 7 programs:
  - CAST: BSIT
  - CABM-B: BSBA-FM, BSBA-MM, BSBA-OM, BSA
  - CABM-H: BSTM, BSHRM
- Roles (`users.role` enum, exactly these four): `admin`, `coordinator`, `supervisor`, `student`. `supervisor` means company supervisor (see `CompanySupervisor`, linking a `supervisor`-role user to a `Company`). There is no separate "adviser/instructor" role.
- User deactivation is **soft** (`is_active = false`) — there is no hard-delete route for users, since a deactivated student/supervisor's journal entries and weekly logs must stay intact. `Admin/UserController::activate()`/`deactivate()` both already existed, but `AdminUsersPage.vue` only ever called `deactivate()` (mislabeled "Delete") with no way back — an admin deactivating a user had no UI path to reactivate them, even though the backend endpoint worked. Fixed: the button is now labeled "Deactivate", and an inactive row shows "Reactivate" instead (calling the pre-existing `activate()` endpoint) — no backend changes needed, both routes already existed. `AdminUsersPage.vue`'s role filter now offers **All Users** (default) / Student / Coordinator / Supervisor (Supervisor was missing entirely before), and `Admin/UserController::index()` unconditionally excludes `role = 'admin'` regardless of filter — this page manages day-to-day accounts, not the single admin account itself (`test_index_never_returns_admin_accounts` in `UserControllerTest.php`). Each row also gained a **View** button opening a read-only account-details modal (avatar/initials, name, username, email, role, program, department, status, `must_change_password`) — explicitly **not** a password, since passwords are hashed and unrecoverable by design; the modal says so and points to the existing "Issue Temporary Password" flow on System Settings for a locked-out user. Separately confirmed (no code change needed): a completed student's write access is **already** blocked today — `ResolvesStudentEnrollment::activeEnrollment()` (used by every student write endpoint) requires `status = 'active'`, which a `completed` enrollment row never matches, while `currentEnrollment()` (used by reads) allows `active` **or** `completed` — so "restrict a graduated student to read-only" was already the system's behavior via enrollment status, not `users.is_active`.
- Creating a `student`-role user auto-creates a matching `student_profiles` row via `UserObserver` (on the `User` model's `created` event), with a placeholder `student_id_number` (`PENDING-XXXXXXXX`) until the real registrar ID is filled in.
- SIPP compliance documents referenced by the system: OJT Annual Report, Summary Report on Student Exit Interview (report itself out of scope), Student Information Sheet (**two variants, both built** — the per-student individual sheet, and the per-company **GROUP** sheet whose reference lives at `docs/Student Information Sheet (Group) (1) (3).pdf` — see the "GROUP Student Information Sheet" bullet below).

## Roles & Configuration
- Admin creates accounts (`Admin/UserController`) and global structure (departments, programs, companies). Creating a student user does **not** enroll them — see below.
- Coordinators own `batches` for their program(s) (`Coordinator/BatchController`) and enroll students into a batch (`Coordinator/EnrollmentController`), which creates the `batch_students` row. `batch_students` is the **authoritative student↔company/supervisor linkage**, with a **DB-level `UNIQUE(batch_id, student_id)`** backstop — at most one row per (batch, student) pair, ever; a row's `status` (`active`/`completed`/`dropped`) carries its lifecycle. Student-facing **WRITE** endpoints (journal/weekly-log save + submit, info sheet, weekly activity logs) require an active (`status='active'`) row via `ResolvesStudentEnrollment::activeEnrollment()` and 422 with "You are not currently enrolled in an active OJT batch." without one; journal/weekly-log **READ** endpoints (show/index/calendar/PDF) instead use `currentEnrollment()` (latest `active` OR `completed`), so a completed student keeps full read access. **All enrollment placement flows through `App\Services\EnrollmentService::enrollOrReactivate()`** (used by `EnrollmentController::store`, info-sheet Accept, and `BatchRosterController::add`): it reuses ANY existing row for the exact (batch, student) pair regardless of status — refreshing `company_id`/`supervisor_id`/`assigned_division` and setting it back to `active` — and only creates a fresh row when none exists, which is what makes the unique index safe.
- **The OJT journal window is REAL-TIME, not estimate-bound** (`ResolvesStudentEnrollment::ojtRange()`): start = the batch's `start_date`, end = `batch_students.completed_at` once the coordinator marks the enrollment completed, or **today** (rolling) while it's still active. The info sheet's `ojt_info.ojt_start_date`/`ojt_end_date` are **informational only** — they render on the form/PDF but gate nothing. The **completion signal** is coordinator-driven from the batch roster modal (`BatchRosterController::complete`/`reopen`, `PATCH batches/{batch}/roster/{batchStudent}/complete|reopen`, confirm-first + toast like drop/reactivate): `complete` requires an active row (422 otherwise) and sets `status='completed'`; `reopen` requires a completed row and is blocked if the student is active elsewhere. `completed_at` is maintained **only** by a `BatchStudent::booted()` saving hook (stamped on entry to `completed`, cleared on exit — `EnrollmentController::update` and every other instance save get it for free; don't set it manually). Downstream: a completed student's writes 422 (`isEditableDate` also requires `status='active'`), the journal calendar freezes its upper bound at `completed_at` (days past it are `no_entry`; while active, days after today stay `future`), the student weekly-logs list ends at the completion week (it **starts** at the Monday of the student's first daily entry or earliest weekly log in the batch — empty list until some work exists), `WeeklyBundlingService` skips them (it only iterates `status='active'`; their existing logs persist), and `User::isInfoSheetGated()` treats an active **or completed** enrollment as having cleared intake so completing a legacy student doesn't re-gate them.
- Coordinators are assigned to a department via the `coordinator_departments` pivot (`User::departmentsCoordinated()` / `Department::coordinators()`), and admins manage the assignment from the Admin Departments page (`Admin/DepartmentController::assignCoordinator`/`removeCoordinator`). **As of the 2026-07-12 admin migration (`enforce_single_department_per_coordinator`), this is one department per coordinator** — `coordinator_departments.coordinator_id` is now unique, `AssignCoordinatorRequest` rejects assigning a coordinator already attached elsewhere, and `Admin/UserController::store` takes a single `department_id` (not `department_ids[]`). This superseded the earlier "a coordinator can run multiple departments" design — a department can still have multiple programs and multiple coordinators, just not the reverse. A coordinator's programs are resolved via `User::coordinatorProgramIds()` — every program in their assigned department, merged with the programs of batches they already coordinate (`batchesCoordinated()`, kept only as a backward-safety net) — not `batchesCoordinated()` alone. `users.program_id` is retained (still used by account creation/`StoreUserRequest`) but is **no longer** the coordinator scoping source.
- **Enrollment is student-driven, coordinator-gated intake — the Student Information Sheet is the gateway** (this superseded the old "enroll first, fill sheet after" model). End-to-end flow:
  1. **Coordinator creates the student login** on the Users → Interns page (`EnrollmentController::createAccount`, `CreateAccountRequest`): NAME, **USERNAME** (no email), PASSWORD, optional STUDENT ID, **PROGRAM** (scoped to their department) + **BATCH** (one they coordinate, belonging to that program). The account is created **NOT-ENROLLED**; the coordinator's intended placement is recorded as a **DRAFT `student_information_sheets` row whose `batch_id` is the intended batch** — the single home for "intended batch before Accept" (no new column). `enrollment-options` now also returns the coordinator's `batches` (with `program_id`) so the form filters the Batch dropdown by the chosen program. Account creation is still distinct from enrollment.
  2. **The student is GATED** until their sheet is `approved`: `EnsureInfoSheetApproved` middleware (alias `infosheet.approved`) wraps a gated student route subgroup in `routes/api.php` — only `student/info-sheet` (show/store), `student/info-sheet/pdf`, `student/companies`, and `student/password` stay ungated; every other student endpoint 403s. `User::isInfoSheetGated()` is the single source of truth (gated unless an approved sheet OR an active enrollment exists — the latter keeps legacy directly-enrolled students working), surfaced on `/api/user` as `student_gated` for the frontend router guard (`web/src/router/index.ts`) + `StudentLayout` nav filtering.
  3. **The student fills + submits the sheet** (`StudentInfoSheetPage.vue`, matching the client reference: Student Trainee Information + Internship Company Information; the on-screen form itself has no sketch input, though the exported PDF gained a blank sketch box — see item 5 below). `Student/StudentInfoSheetController::store()` **no longer requires an active enrollment** — it writes the scaffolded draft (or falls back to an active enrollment's batch for legacy students), re-derives the read-only Program/Coordinator from the intended batch (anti-spoof), and clears any prior rejection. **Name of Company is the one constrained field** — a dropdown from `GET student/companies` (active companies); it stores both `ojt_info.company_id` (drives Accept) and `host_company` (name). **Year Level is a constrained dropdown** (`1st Year`..`4th Year`, validated via `in:` in `StoreInfoSheetRequest`), not free text. **An approved (enrolled) sheet is no longer permanently read-only** (this supersedes the earlier "approved = fully locked" design): `store()` still blocks a fresh gate submission from replacing it, but now allows **partial post-enrollment editing** — **Program & Year and the assigned Company stay locked** (re-derived server-side from the existing sheet, ignoring whatever the client sent, since they drove the coordinator's Accept step), while personal info, company address, signatory, supervisor, schedule, and dates remain freely editable for routine profile upkeep. Saving an already-`approved` sheet **never** moves it back to `draft`/`submitted`/clears its `rejection_reason` — `submission_status` stays pinned to `approved` — so routine edits can't accidentally re-trip `EnsureInfoSheetApproved` and re-gate an already-enrolled student. For a not-yet-approved sheet, status flow is unchanged: `draft`/`submitted`/`rejected` are fully editable (`submission_status` enum has `'rejected'` + a nullable `rejection_reason`). Submit confirms first + toasts.
  4. **The coordinator reviews on Student Info Sheets** (`Coordinator/CoordinatorInfoSheetController`, `CoordinatorInfoSheetsPage.vue`) — now an **Accept/Reject queue scoped by the sheet's intended-batch program** (so NOT-yet-enrolled students finally appear; the old enrollment-only scoping couldn't surface them), with status/program filters. **Accept = enroll** (`accept`): creates the active `batch_students` row for the sheet's batch + the student's chosen company + **that company's Company Supervisor**, then marks the sheet `approved` (lifting the gate). Only a `submitted` sheet is acceptable (re-accept is a no-op 422, never double-enrolls); a chosen company with no supervisor 422s. **Reject** (`reject`, `RejectInfoSheetRequest`) sets `rejected` + a required reason shown to the student, who edits + resubmits. Both are scope-enforced (403 out of scope). Enrollment is shared via `App\Services\EnrollmentService::enrollOrReactivate()`, reused by both `EnrollmentController::store` and Accept.
  5. **Individual Info Sheet PDF** (`pdf.info-sheet` blade via the shared `BuildsInfoSheetPdf` trait): official MDC document with the logo embedded as a base64 data URI from `public/images/mdc-logo.png` (labeled-placeholder fallback if absent), the college/program header, the two labeled sections, plus a **"Sketch of Internship Company Location" box** (bordered, blank, 35mm tall) at the bottom of the page — reinstated in commit `b401733`, reversing the earlier "no sketch box" decision recorded in this file; the on-screen `StudentInfoSheetPage.vue` form itself still has no sketch input, this is PDF-only. Downloadable by the student (`GET student/info-sheet/pdf`, own) and the coordinator (`GET coordinator/info-sheets/{student}/pdf`, in-scope; 403 otherwise) — "Download PDF" buttons on both surfaces.
- The **Annual SIPP Report** (`Coordinator/AnnualSippReportController`, page `web/src/pages/coordinator/CoordinatorAnnualSippPage.vue`) is **per-program** — a secondary nav shows one tab per program in `User::coordinatorProgramIds()` scope; an out-of-scope program 403s. Candidate rows are sourced one-per-daily-journal-entry from students' `sipp:true` journal fields (`issues_concerns`/`solutions`/`recommendations`), joined to `batches` by `program_id` + `academic_year`. The coordinator curates (edit any of the 3 cells, include/exclude, delete row) — curation, signatories, and the editable "DEGREE PROGRAM" heading persist in `sipp_annual_reports.report_data` (JSON), keyed by coordinator+program+AY (`program_id` added nullable, `batch_id` made nullable). Only included rows export via dompdf (`resources/views/pdf/annual-sipp-report.blade.php`, official-document layout).
- The **HTE & Student Interns List** (`Coordinator/HteReportController`, page `web/src/pages/coordinator/CoordinatorHtePage.vue`) is a **separate** coordinator report from the Annual SIPP Report. It is a single **combined list per academic year** (not per-program tabs) covering all programs in `User::coordinatorProgramIds()` scope. Candidate rows are derived one-per-enrollment from `batch_students` (joined to `batches` by `program_id` + `academic_year`), mapped to the 5 official columns: host establishment (`company.name`), student name ("Last, First M." when a clean split exists), program (code + year level, e.g. `BSIT-4`), gender (`student_profiles.sex`), and duration (batch `start_date`–`end_date`). The coordinator curates (edit any cell, include/exclude, delete, **add a manual row** for incomplete data) and edits editable signatories; curation persists as an override layer in the new `hte_reports.report_data` (JSON), keyed by coordinator + nullable `program_id` + AY, leaving source enrollments untouched. An optional `program_id` query filter is authorized against scope (403 out-of-scope), mirroring `AnnualSippReportController`. Only included rows export via dompdf (`resources/views/pdf/hte-report.blade.php`, official-document layout).
- The four other coordinator pages are now **real + department-scoped** (via `User::coordinatorProgramIds()`, out-of-scope 403s): **Dashboard** (`CoordinatorDashboardController`) — active-intern count, journals submitted vs missing this week (Mon–today), active batches, and a "students behind" list (in-scope active interns with ≥1 `missing`/`overdue` daily entry this week); **Journal Activities** (`CoordinatorJournalActivityController`) — read-only monitoring, default = today, filterable by `from`/`to` (Y-m-d) date range + `company_id` + `program_id` + `status` (see below for the detail view), per-student submitted/missing tally over a range (use `whereDate`, not raw `whereBetween`, so same-day matches hold under SQLite's datetime storage); **Partner Companies** (`CoordinatorCompanyController`) — scoped CRUD where scope = companies used by the coordinator's department students **plus companies not yet linked to any enrollment** (no creator column exists, so unlinked ⇒ visible, which keeps freshly-created companies in view), with a supervisors panel that attaches an existing `supervisor`-role user or creates+attaches a new one inline via `company_supervisors`; **Student Info Sheets** (`CoordinatorInfoSheetController`) — read-only view of in-scope students' latest sheets (info-sheet PDF export is deferred to the Student page cleanup, marked with `TODO(student-cleanup)`). `companies.description` (nullable text) was added for the companies form.
- Coordinators can create **student or supervisor login accounts** from the Interns page (`EnrollmentController::createAccount`, `CreateAccountRequest`): role is restricted to `student`|`supervisor` only (never coordinator/admin), password hashed, `is_active` true, and a student also gets a `StudentProfile` (a student's `program_id` must be in the coordinator's scope). This is **account creation only, distinct from enrollment** — a created student still must be enrolled into a batch (company + supervisor) via `EnrollmentController::store`; the Interns page keeps the two as separate controls.
- The daily-journal length limit is **character-based**: `journal_templates.char_limit` (renamed from `word_limit`, default **1500**) validates the whole entry's combined content with `mb_strlen` in `StoreJournalEntryRequest`; per-SIPP-field cap stays at **300** chars. Coordinators set it on the Journal Templates page ("Character Limit"), and the student write page counts characters (`X / char_limit`). The journals-list `word_count` display attribute is a separate, unrelated concern.
- **Daily journal locks only once its week is bundled, not on submit** (this supersedes the earlier "one-submission lock" design — a submitted entry is no longer permanently frozen the moment it's submitted): `Student/JournalEntryController::store()` now 422s ("This week has already been compiled into your Weekly Log and can no longer be edited.") only once `isBundledWeek()` finds a `WeeklyLog` row for that date's Mon-Fri week (student+batch) — i.e. once `WeeklyBundlingService` has compiled the week at least once, via the **Monday** schedule (moved off Saturday — see the Weekly Bundling bullet; a Saturday run used to lock the week before a Saturday shift began, making a genuinely-worked Saturday unwritable) or the admin on-demand trigger. Until then, a student can freely resave any date in their editable range, submitted or not — there is still no return-for-revision concept for individual daily entries; the correction surface is the weekly narrative itself once bundled. This is a **one-way lock**: even if the resulting `WeeklyLog` is later returned by a supervisor for revision, the underlying daily entries stay locked. `isEditableDate()` is now a thin wrapper over a new `lockedReason()` (`'not_active'` | `'range'` | `'bundled'` | `null`), and `show()` exposes that `locked_reason` so `StudentWriteJournalPage.vue` can show the right banner copy instead of one generic message. The `date`-cast-column gotcha below still applies inside `store()` (it fetches the existing row via `whereDate`, not plain equality).
- **Journal templates are many-programs-per-template**: `journal_templates.program_id` was dropped in favor of the `journal_template_program` pivot with **`UNIQUE(program_id)`** (a program belongs to **at most one** template, ever — the pivot is the single source of truth). Relations: `JournalTemplate::programs()` / `Program::journalTemplates()` (both `belongsToMany`; a program's template is `journalTemplates()->first()`). Template create/update take **`program_ids[]`** (required, min 1, each in `coordinatorProgramIds()`); a program already claimed by a **different** template 422s (naming the conflict, so `UNIQUE(program_id)` never surfaces as a 500); `store/update` `sync()` the pivot. `index()` returns each in-scope program with a nullable **`assigned_template_id`** so the UI can grey out already-covered programs. A batch still resolves its template via **`batches.journal_template_id`** (unaffected by the drop); the two coordinator batch requests validate that FK against the pivot. **SIPP (Annex C) is a fixed trio** keyed `issues_concerns`/`solutions`/`recommendations` — a section may only be flagged `sipp=true` if its key is one of those three (server-guarded in `ValidatesJournalTemplate`; the frontend owns adding/removing the trio). `journal_templates.is_active` stays (soft on/off), relabeled in the UI as **"Available for use in batches"** (helper: "Turn off to retire this template without deleting its history."). The template editor (`web/src/pages/coordinator/CoordinatorJournalTemplatesPage.vue`) never shows the raw section `key` — it's always auto-generated from the section `label` (still sent in the payload). Program assignment is a **multi-select checkbox list**; a program already claimed by another template renders **disabled + greyed** ("(unavailable — claimed by another template)") via `assigned_template_id`, while programs already on the template being edited stay selectable. SIPP is authored as **one checkbox** ("Include SIPP Report (Annex C)") that adds/removes the fixed trio together inside one bordered container — there is no per-section SIPP checkbox in the UI. The modal caps its height (`max-h-[calc(100vh-4rem)]`) with a pinned header/footer and an internally-scrolling body, so a long template's form is reachable top-to-bottom (the previous centered-overlay-scrolls-itself layout made the top unreachable). The student write page (`StudentWriteJournalPage.vue`) mirrors this: the SIPP trio lives inside one bordered container revealed by a single "SIPP Report" checkbox (`sippEnabled`), respecting the 300-char SIPP field limit. On `CoordinatorBatchesPage.vue`, the batch's Journal Template dropdown filters by **membership** in `template.programs[]` against the batch's selected program (not the old single `program_id`), and templates are **refetched every time the create/edit batch modal opens** so a template created moments earlier shows up immediately.
- The two official report PDFs carry annex labels top-right: the **Annual SIPP Report is Annex "C"** (`resources/views/pdf/annual-sipp-report.blade.php`) and the **HTE & Student Interns List is Annex "D"** (`resources/views/pdf/hte-report.blade.php`); both use a clean/white table header (no gray fill) and a "(Name and Signature)" caption under each signatory block.
- **Coordinator UX rule**: crucial/destructive actions (delete a report row, deactivate a template, deactivate a batch/company, remove a supervisor/coordinator) prompt a **confirm dialog first**; successful saves show a **toast after**. Use the shared helpers in `web/src/lib/toast.ts` (`confirmAction` — now an **async** promise-based styled modal, NOT `window.confirm` anymore; `showToast(message, type, timeout?)`) with `web/src/components/ToastHost.vue` mounted on the page (per-page, not layout-level — a page using either helper must mount it itself). `ToastHost` renders a fixed top-right stack: white card, colored left border + matching icon (green check / red exclamation) per `type`, shadow, and a `TransitionGroup` fade/slide. This confirm-first-destructive + toast-after-success pattern is enforced consistently across coordinator, student, supervisor, and admin destructive actions (delete/remove/deactivate/drop) — not just coordinator. **Toast durations auto-scale, aren't dismissible-by-default, and are capped** (this pass hardened the previously bare-bones toast queue): `timeout` is now optional — when omitted, `showToast` derives it via `defaultTimeoutFor(message, type)` (3s base, +50ms per character past a 20-char grace window, capped at 8s; `error` toasts get a 4.5s floor even when short, since severity is its own importance signal, not just length) — none of the ~40 existing call sites pass an explicit timeout, so all of them picked up auto-scaling for free. A `MAX_VISIBLE_TOASTS = 4` cap evicts the oldest toast (clearing its timer) once exceeded, so a burst of actions can't stack the queue indefinitely. Each toast now has a close (×) button (`dismissToast(id)`) and pauses its countdown on `@mouseenter`/resumes on `@mouseleave` (`pauseToast`/`resumeToast`, both new exports) — per-toast timer state (`timerId`/`remaining`/`armedAt`) lives in a module-level `Map` in `toast.ts`, deliberately kept off the reactive `Toast` object so the template only ever sees `id`/`message`/`type`. No call site changes were needed anywhere — the improvements are entirely internal to `showToast`/`ToastHost.vue`.
- **The supervisor is tied to the company, never a manually-picked person** (this supersedes the earlier "Supervisor-by-company filtering" design, where the coordinator picked company AND supervisor as two independent dropdowns): `EnrollmentService::enrollOrReactivate()` no longer takes a `$supervisorId` parameter at all — every caller supplies only a `$companyId`, and the service derives `supervisor_id` itself from `Company::loginSupervisor()->user_id`, aborting 422 ("This company has no supervisor account yet...") if the company has none. - **Google OAuth: email verification + link-only sign-in** (`laravel/socialite`, `App\Http\Controllers\Auth\GoogleController`). Two intents through **one** controller and **one** callback:
  - **`intent=verify`** — a signed-in user of ANY role proves they own a Gmail address. **Google SUPPLIES the address**, it is not confirming one the user typed: the flow writes both `users.email` and `users.email_verified_at` in one step, so a typo is impossible. Rejected if Google itself reports the address unverified, or if it already belongs to a **different** account (`users.email` is unique — claiming it would steal their sign-in or hit the constraint).
  - **`intent=login`** — signs in an account matched on `LOWER(email)` **AND** `email_verified_at IS NOT NULL`. **Both halves are the guard.** Because this controller is the only thing that ever sets that column, non-null means Google established the binding, so an address merely typed by an admin or student can never be signed into (which is what stops a typo'd email handing a stranger someone's account). **It NEVER creates an account and never assigns a role** — accounts are staff-provisioned, so an auto-created OAuth user would have no role, no program, no enrollment; an unrecognised address gets `not_linked`, and `test_an_unknown_google_address_creates_nothing` asserts `User::count()` is unchanged. A deactivated account gets `deactivated`, mirroring `LoginRequest`'s existing message.

  **Why it is safe without Socialite's session state:** the flow uses `->stateless()` with an **encrypted state** (`Crypt::encryptString` of `{intent, user_id, nonce, expires_at}`, 10-minute TTL) plus the same `nonce` in a short-lived **httpOnly `SameSite=Lax` cookie**, compared with `hash_equals` on callback. The cookie double-submit replaces the CSRF protection `stateless()` gives up — including *login* CSRF, where there is no user yet to bind state to — and, unlike a session, cannot be lost on the round trip once the SPA and API are on different domains. `SameSite=Lax` is deliberate: it still rides the top-level GET redirect back from `accounts.google.com`.

  **Both flows send `prompt=select_account`, and that is a security control, not a preference.** Without it Google *silently* auto-selects when exactly one account is signed into the browser — so on a shared machine (computer lab, borrowed laptop) a student clicking "Sign in with Google" would be signed straight in as whoever last used Chrome, with no password and no prompt. The verify flow needs it equally: silent selection there binds someone else's Gmail onto your account, and since a verified address is what authorises Google sign-in, that grants them a permanent way in. Deliberately Google's own chooser rather than a confirmation screen of ours — the account state lives on Google's domain, so only Google can truthfully list the available accounts and offer "use another account". Covered by `test_both_flows_force_googles_account_chooser`.

  **Routes are WEB routes** (`routes/web.php`), not `api/*`, because all three are top-level browser navigations: `GET auth/google/verify` (`auth`), `GET auth/google/login` (**deliberately NO `guest` middleware** — see below), `GET auth/google/callback` (no auth — the encrypted state authenticates it). All three are `throttle:10,1`, since the `api` group's limiter does not cover web routes and `LoginRequest`'s 5-attempt limiter does not apply here. **One callback for both intents means only ONE redirect URI to register in Google Cloud.**

  **Two redirect-target rules, both learned the hard way on 2026-07-27 — do not "simplify" either back:**
  1. **`auth/google/login` must NOT carry the `guest` middleware.** That middleware redirects an already-authenticated user to `/`, which on the API origin is `routes/web.php`'s root route — i.e. the browser lands on `{"Laravel":"13.17.0"}` at `localhost:8000`, a dead end on a different host from the SPA. `redirectToLogin()` handles the already-signed-in case itself by sending them to their dashboard.
  2. **Every success redirect goes to `/{role}/dashboard`, NEVER to `/`.** The SPA's root route is an unconditional `{ path: '/', redirect: '/login' }`, and `router/index.ts`'s `beforeEach` only calls `auth.fetchUser()` for routes marked `requiresAuth` — so a browser landing on `/` with a perfectly valid session never asks the server who it is and gets bounced to the login page. The observed symptom was a successful Google sign-in that *looked* like it failed: the user was returned to the login page, and clicking "Login" then merely rode the session the callback had already created. `dashboardPathFor()` mirrors `roleRedirect()` in the router. (The same papercut still affects typing the bare SPA origin while logged in — pre-existing, not Google-specific, and not fixed.)

  **Editing an email revokes verification, and therefore Google sign-in** — `ProfileController::update()` and `Admin\UserController::update()` both null `email_verified_at` whenever `email` actually changes (via `forceFill`, since it is deliberately not mass-assignable). This is also the un-link mechanism; there is no separate "unlink Google" action.

  **Deliberately NOT done: the `MustVerifyEmail` interface is not added to `User`.** It is unnecessary (`markEmailAsVerified()` already exists via the trait `Illuminate\Foundation\Auth\User` uses), and adding it would activate the framework's `SendEmailVerificationNotification` listener on the `Registered` event — which the still-unguarded `POST /register` fires. The `verified` middleware alias therefore stays applied to **zero** routes: **verification gates email delivery and Google sign-in, never app access**, because coordinator-created students have no email at all and a `verified` gate would lock out exactly the population intake produces.

## Architecture Notes
- **Routing**: `routes/api.php` defines `/ap~~i/user` (auth:sanctum) plus an `admin/*` group gated by `auth:sanctum` + `role:admin`. Role gating middleware is `App\Http\Middleware\EnsureRole`, aliased as `role` in `bootstrap/app.php`, used as `->middleware('role:admin')` or `role:admin,coordinator` for multi-role routes. It also blocks `is_active = false` accounts with a 403 before checking role.
- **Controllers**: `app/Http/Controllers/Admin/*` for admin-only endpoints, `app/Http/Controllers/Auth/*` for Breeze/Sanctum auth flows. Follow the existing Form Request + Controller pattern (one Form Request per create/update action in `app/Http/Requests/{Admin,Auth}/`) before inventing new patterns.
- **Web SPA structure**: pages live in `web/src/pages/{admin,coordinator,student,supervisor}/`, role-specific shells in `web/src/layouts/*Layout.vue`. **Those four layouts are self-contained** — each renders its own sidebar/header directly and shares only the smaller pieces (`SidebarCollapseToggle`, `NotificationBell`, `ProfileMenuPopover`). There is no shared `DashboardShell` wrapper; that component existed but was referenced by nothing and was deleted on 2026-08-04. Routes are defined centrally in `web/src/router/index.ts`, gated by `meta: { requiresAuth, role }` and a global `beforeEach` guard that calls the Pinia `auth` store (`web/src/stores/auth.ts`). API calls go through the shared Axios instance at `web/src/lib/axios.ts`.
- **Dev proxy**: `web/vite.config.js` proxies `/api`, `/sanctum`, `/login`, `/logout`, `/register`, `/forgot-password`, `/reset-password` to the Laravel backend (`VITE_BACKEND_URL`, default `http://localhost:8000`) so the Vite dev server at `:5173` can make same-origin requests.
- **CORS/Sanctum config**: `FRONTEND_URL` and `SANCTUM_STATEFUL_DOMAINS` in `.env` must match wherever `web/` is actually running — check `.env.example` when debugging auth/CORS issues.
- **Deployment — DECIDED STACK + what shipped for it (2026-07-28).** **The operational runbook is `docs/DEPLOYMENT.md`** (written for whoever clicks through the dashboards — prerequisites, every env var, post-deploy verification commands, and a symptom→cause troubleshooting table); this bullet is the *decision record* behind it and the current word on deployment; the longer historical bullet below it records the reasoning that led here, and two of its claims are now **corrected** (see the end of this bullet). Chosen stack, driven by a hard **$0 / no-credit-card** constraint for the capstone defense:
  - **SPA → Vercel Hobby** (free). Root Directory `web`, config in **`web/vercel.json`**.
  - **API → Render free web service, via Docker** (free, no card). It **spins down after 15 minutes idle and takes 30-60s to wake** — mitigate before a demo with a free external pinger (cron-job.org / UptimeRobot) hitting `/up`, or just load the site a minute early.
  - **DB → Aiven always-free managed MySQL** (free, no card, 1GB). Deliberately **not** Render's free Postgres, which **expires 30 days after creation** and would also force a MySQL→Postgres engine switch shortly before a defense.
  - **Cron → an external scheduler pings `/api/cron/run` hourly** (superseded 2026-08-02; this bullet previously read "not deployed"). Render cron has no free tier, so the three commands in `routes/console.php` never ran there — and the fallback this bullet used to name, the admin System Settings manual triggers, was **deleted** on 2026-08-01, so for a day there was no path at all. See the `CronController` changelog entry. Operator setup lives in `docs/CRON-AND-EMAIL-SETUP.txt` (written for Carlo, who owns the Render deploy); `docs/DEPLOYMENT.md` §1/§4/§9/§10 were corrected to match.
  - **Avatars → still the local `public` disk**, i.e. discarded on every redeploy. R2 is fully wired and is a **pure env flip** (`AVATAR_DISK=r2` + the `R2_*` vars); it was left off because enabling R2 requires a card on Cloudflare.

  **Deploys track a dedicated `deploy` branch — pushing to `main` does NOT deploy anything** (project owner's call, 2026-07-28). `render.yaml` sets `branch: deploy`, and `web/vercel.json` carries `git.deploymentEnabled: {main: false}` so Vercel refuses to build main at all; Vercel's **Production Branch must also be set to `deploy`** in its dashboard to match (there is no vercel.json field for it). Shipping is deliberate: `git checkout deploy && git merge main && git push origin deploy`. The reason this is not just tidiness — `docker/entrypoint.sh` runs `migrate --force` on **every** boot, and the API sleeps and re-boots on idle, so with auto-deploy on main a half-finished migration would reach live data on the next wake, and any broken commit would take the demo down. What is and isn't affected by ongoing work: local edits and commits have **zero** effect on the deployed copy; the **Aiven database is external**, so redeploys and sleep/wake cycles never touch the data; the only thing lost on a redeploy is uploaded avatars, because the container filesystem is ephemeral (`AVATAR_DISK=public`).

  **The SPA↔API model is a same-origin rewrite proxy, not cross-domain CORS.** `web/vercel.json` rewrites `/api/*`, `/sanctum/*`, `/auth/google/*`, `/auth/login`, `/auth/logout`, `/forgot-password`, `/reset-password` to the API host, plus a catch-all `/:path*` → `/index.html` for the SPA's `createWebHistory()` deep links. The browser therefore only ever sees one origin, which means **CORS never fires, `SameSite=None` is not needed, and login does not depend on third-party cookies** (the fragile part of the cross-domain alternative — Safari and hardened browsers block them). Consequences that are load-bearing:
  - **`SESSION_DOMAIN` must be EMPTY** so the session cookie is host-only and attaches to the Vercel domain the browser believes it is talking to. Setting it to the API's domain breaks login.
  - **`SANCTUM_STATEFUL_DOMAINS` must be the VERCEL host**, not the API's. Sanctum decides "is this the frontend?" from the request's Referer/Origin, and through the proxy that is the Vercel domain. Wrong value ⇒ every authenticated request 401s while `/login` itself appears to succeed.
  - **`GOOGLE_REDIRECT_URI` must point at the VERCEL origin** (`https://<app>.vercel.app/auth/google/callback`), and that exact string must be registered on the OAuth client. **This REVERSES the older "set it to the production API origin" instruction below.** Reason: the callback signs the user in, and the browser stores that session cookie against whichever host it thinks it called — send Google straight to the API and the cookie lands on the API's domain while the SPA reads the Vercel domain, so sign-in silently appears to fail.
  - **`SESSION_SAME_SITE=lax` is correct here** (not `none`), because the requests are first-party. Lax still rides the top-level GET redirect back from `accounts.google.com`.

  **`POST /register` was REMOVED** (`routes/auth.php`, and `Auth\RegisteredUserController` deleted). Breeze's self-service registration created an **active `role: student` account for any anonymous caller, unthrottled** — on a public URL that means a stranger self-enrolls and lands in a coordinator's info-sheet queue. The SPA never referenced it. Two side effects: the `Registered` event no longer fires anywhere (which was the stated reason adding `MustVerifyEmail` to `User` would have been unsafe), and the now-pointless `/register` entry was dropped from `web/vite.config.js`'s proxy. `tests/Feature/Auth/RegistrationTest.php` was replaced by **`RegistrationClosedTest`**, which asserts the endpoint 404s, that no route is named `register`, and that login still works.

  **`/login` had to be split from the SPA's own page route.** The SPA now posts credentials to **`/auth/login`** (and **`/auth/logout`**), which both the Vercel rewrite and the Vite dev proxy map back to the API's real `/login`/`/logout` — **no backend route changed**. Necessary because `/login` is simultaneously Laravel's POST endpoint and the SPA's router page path, and **Vercel rewrites match on path only, never on HTTP method**, so proxying `/login` wholesale would send a page refresh (GET) to Laravel, which only defines POST there, and answer **405**. This also retired the `bypass: req => req.method === 'GET' && '/index.html'` hack that existed in `vite.config.js` for the same collision. Verified live through the dev proxy: `GET /login` → 200 HTML, `POST /auth/login` → 200 + user payload, `GET /api/user` → 200 authenticated.

  **`$middleware->trustProxies(at: '*')`** was added in `bootstrap/app.php`. Laravel trusts **no** proxies by default (`TrustProxies::handle()` calls `setTrustedProxies([])` unless configured), so behind Vercel's proxy it ignores `X-Forwarded-For` and reports the edge IP as `$request->ip()` — putting **every unauthenticated visitor in one rate-limit bucket**, which matters for the `api` limiter's guest fallback and for the outright per-IP `throttle:10,1` on the Google OAuth routes. Trade-off knowingly accepted: `'*'` lets a caller spoof `X-Forwarded-For` to dodge throttling, but Vercel publishes no stable edge-IP list, and an accidental shared-bucket lockout is the likelier harm.

  **`config('app.timezone')` is now `env('APP_TIMEZONE', 'UTC')`** and deployments set **`Asia/Manila`**. Every user is UTC+8, and on a UTC server anything before 08:00 Manila still reads as **yesterday** — so the journal calendar offers the wrong date, "this week" counts on both dashboards are off, and per-student reminder hours fire 8 hours early. The **default stays UTC on purpose** so the test suite's `Carbon::setTestNow` travel behaves exactly as before.

- **Deployment (historical reasoning — see the DECIDED STACK bullet above for what actually shipped)**: `web/` (the Vue 3 SPA) deploys to **Vercel** (static build — a good fit, since it's just a Vite-built static site). The Laravel API deploys **separately, on a different host** — Vercel does not natively support PHP/Laravel: no persistent process for the scheduled console commands in `routes/console.php` (weekly bundling every **Monday**, the nightly 2am archive purge, and **hourly** missing-journal reminders), an ephemeral function filesystem, and no built-in persistent database — so only the SPA half of this monorepo goes there. **Reminder email raises the stakes on that:** it needs the API host to run **both** `schedule:run` (every minute, so the hourly reminder command actually fires) **and** a queue worker — so "the API host must support cron + a long-running worker" is now a functional requirement, not just a nice-to-have. **Google OAuth adds three more deploy obligations:** set `GOOGLE_REDIRECT_URI` to the **production API** origin and register that exact URI on the OAuth client (scheme, host and port must match or Google refuses); set the SPA's `VITE_BACKEND_URL` to the API origin, since the Google buttons are real navigations to the API host and the dev Vite proxy does not exist in production; and publish the OAuth consent screen (otherwise only Gmail addresses listed under Test users can sign in). The API host is expected to have an **ephemeral filesystem** (container-based, not a persistent VPS disk) — this is why avatar storage should move off the local `public` disk to an S3-compatible provider (Cloudflare R2 recommended: free tier that doesn't expire, no egress fees, drop-in compatible with the `s3` disk already defined in `config/filesystems.php`) before that API deploy happens; not yet implemented as of this note.
- **Gotcha: `APP_URL` must carry the port, or every uploaded avatar is a broken image.** `config/filesystems.php`'s `public` disk sets `'url' => rtrim(env('APP_URL'), '/').'/storage'`, and `User::avatarUrl()` builds `avatar_url` (on every JSON user payload) from it. Laravel's stock `APP_URL=http://localhost` therefore emits `http://localhost/storage/avatars/x.webp` — **port 80**, which on the owner's machine is Laragon's Apache, not `php artisan serve` on :8000 — so the browser got a 404 and the Edit Profile / header avatar rendered as a broken image while the file sat perfectly fine on disk. **Fixed 2026-07-26 by setting `APP_URL=http://localhost:8000` in both `.env` and `.env.example`** (verified end-to-end: an authenticated `GET /api/user` returns `http://localhost:8000/storage/avatars/…webp` and that URL returns `200 image/webp`). If you ever run `artisan serve --port=NNNN`, `APP_URL` has to follow. Deliberately **not** solved by adding `/storage` to `web/vite.config.js`'s proxy: `avatar_url` is absolute, so the proxy would never see it, and absolute URLs are what the eventual split Vercel-SPA / separate-API-host deploy needs anyway. **Debugging tip / red herring:** a missing file under `/storage/…` returns **403 Forbidden, not 404** — the `local` disk has `'serve' => true` with no `'url'`, so `FilesystemServiceProvider::serveFiles()` registers a `storage/{path}` route (`storage.local`) that resolves against `storage/app/private`, while real avatars live on the `public` disk (`storage/app/public`) and are served straight off the `public/storage` symlink/junction before Laravel is ever reached. So on a broken avatar: **404 ⇒ wrong host/port in `APP_URL`; 403 ⇒ the file genuinely isn't on disk.** (Orphan files are normal — `migrate:fresh --seed` nulls `users.avatar_path` but never sweeps `storage/app/public/avatars`.)
- **Gotcha: a Windows PHP build ships NO CA bundle, so every outbound HTTPS call from PHP fails.** The official php.net/WinGet Windows builds leave both `curl.cainfo` and `openssl.cafile` empty, and Guzzle then dies with `cURL error 60: unable to get local issuer certificate`. This is **not** OAuth-specific — it breaks Google's token exchange, SMTP over TLS (so reminder email), and any third-party API call identically. It cost a full debugging session on 2026-07-27 because the symptom was indistinguishable from bad credentials: Socialite's exchange failed and the SPA showed a generic "could not complete the Google sign-in", while the Google Cloud setup had been correct all along. **Fix:** download `https://curl.se/ca/cacert.pem` and point BOTH ini keys at it (on the owner's machine: `C:\Users\User\AppData\Local\php-ssl\cacert.pem`; `php.ini` backed up as `php.ini.bak-before-cacert`). **A WinGet upgrade of PHP replaces `php.ini` and silently wipes both lines** — re-apply them. **Diagnostic rule:** when any integration "just fails", test raw TLS reachability first (a Guzzle `GET` to the provider from `artisan tinker`) before suspecting credentials or app logic. `GoogleController`'s callback now logs the real exception (`Log::warning`, plus `Log::info` on every entry-point and callback hit) precisely so this class of failure is never invisible again — turn `LOG_LEVEL` down from `debug` if that becomes noisy in production.
- **Gotcha: `date`-cast columns and plain equality under SQLite.** MySQL's `DATE` column type truncates any time component on write; SQLite's does not (SQLite has no real column-type enforcement), so a `date`-cast Eloquent attribute written as `'2026-07-06'` can come back out of SQLite storage as `'2026-07-06 00:00:00'`. A plain `where('week_start', $dateString)` — or `updateOrCreate()`'s match array, which is the same thing internally — silently fails to find the row it just created, and a second write inserts a duplicate instead of updating. Always use `whereDate('week_start', $dateString)` for lookups against a `date`-cast column (already the pattern in `WeeklyLogController::show()`/`index()`); this bit both `WeeklyBundlingService::bundleWeek()` and `WeeklyLogController::store()` in the same session before being fixed the same way — check any new code that reads back a `date`-cast column it just wrote.

  **CRITICAL follow-up (2026-07-29) — all four of those sites cached OBJECTS, which cannot work, and every one of them was 500ing in the browser.** `config/cache.php` ships Laravel's default `'serializable_classes' => false` (hardening against gadget-chain attacks if `APP_KEY` leaks). `Illuminate\Cache\DatabaseStore::unserialize()` therefore calls `unserialize($value, ['allowed_classes' => false])`, so **any object** read back from a serializing store (database, file, redis) returns as `__PHP_Incomplete_Class`. A cached `Collection` or Eloquent model consequently **works on the first (cold) request and 500s on every request after it** — `coordinatorProgramIds()` blew its `: Collection` return type, and the two admin reference endpoints serialized garbage. Observed symptom: login succeeded, then the **coordinator dashboard hung on "Loading..." forever** and `admin/programs`+`admin/departments` failed — which read as "the credentials are broken." **Fix: cache plain arrays, re-wrap on read** — `->all()` inside the closure + `collect($ids)` on the way out for `User::coordinatorProgramIds()` and `SystemSetting::cached()`; `->get()->toArray()` for `Admin/ProgramController::index()` and `Admin/DepartmentController::index()` (`toArray()` emits byte-identical JSON, so no API shape changed). Arrays are exempt because there is no class to rebuild. **Deliberately NOT "fixed" by setting `serializable_classes => true` or whitelisting `Collection`** — that would disable a real security control app-wide to patch four call sites. **Rule going forward: never put an object in `Cache::remember()` — cache arrays/scalars and rehydrate.** This escaped the original pass because `phpunit.xml` pins `CACHE_STORE=array`, and `ArrayStore` holds live PHP objects in memory without ever serializing, so the failing read never executed under test; the `tinker` check above only ever exercised a **cold** write+read, never the warm read that actually breaks. Regression coverage is now `tests/Feature/Services/CacheSerializationTest.php` (4 tests) — it forces the **`file`** store with `serializable_classes => false` to reproduce production behaviour, asserts a warm read of each of the four sites, and pins the underlying constraint itself (`test_a_cached_object_would_not_survive_a_serializing_store`) so a future framework/config change that lifts it is announced rather than silent. Confirmed the test genuinely catches the bug by reverting the `User::coordinatorProgramIds()` fix and watching it fail with the exact production error. Full suite: **399 passed**.

  1. **Persistence = a NEW `group_info_sheets` table** (explicitly approved, so Hard Rule #3 is satisfied for this one table). Shape: `coordinator_id` → users, `company_id` → companies, `academic_year` (string, matching `batches.academic_year` like the HTE/SIPP reports), `sheet_data` JSON, `status` draft/finalized, `generated_at`, and `UNIQUE(coordinator_id, company_id, academic_year)` — deliberately mirroring `hte_reports`/`sipp_annual_reports`' column shape (same `$timestamps = false` + `CREATED_AT = 'generated_at'` model convention) so it reads as the third member of that family rather than a new pattern. `sheet_data` holds **everything**: `{header: {department_line}, company: {…10 typed fields}, rows: {id → overrides}, manual_rows: [], deleted_ids: []}`.
  2. **Roster cells ARE coordinator-editable, HTE-style.** The JSON carries the same override structure as `hte_reports.report_data`: per-source-row overrides keyed by enrollment id, `manual_rows[]` for interns with missing/absent data, `deleted_ids[]` tombstones, and include/exclude — source `batch_students` / `student_information_sheets` rows are never mutated. Consequence carried over from `HteReportController::buildRows()`: a curated override whose source enrollment later gets purged still renders from its last-saved snapshot (the exact bug already fixed there — see the `BatchStudentPurgeService` bullet above), built the same way from day one instead of re-introduced. **An override only counts when it is NON-EMPTY** (`trim($saved[$field]) !== ''`), unlike HTE's `$saved[$field] ?? $row[$field]`: an empty string is not null, so HTE's shape would let a single Save taken while a student had not yet filled in (say) their guardian's name freeze that blank permanently and mask whatever they typed later. Here a blank saved cell means "no edit" and the student's own sheet keeps flowing through; the trade-off is that a cell **cannot be blanked** by clearing it — use include/exclude or delete to drop a row instead. Covered by `test_an_empty_saved_override_never_masks_the_students_own_sheet` and `test_a_non_empty_override_still_wins_over_the_students_sheet`.
  3. **The roster table GROWS** — no 12-row cap and no per-page repagination. It renders exactly as many rows as there are included interns; the company block follows the table. (The reference's 12 pre-printed rows are a paper artifact, not a limit.)
  4. **Scope = the coordinator's programs**, via `User::coordinatorProgramIds()`, exactly like every other coordinator page. Enforced by `assertCompanyInScope()`, which doubles as the roster query: a company with **zero** in-scope interns for that AY **403s** rather than rendering an empty sheet, and the company picker (`index`) only ever offers companies that actually host in-scope interns. A company hosting interns from two departments therefore yields one sheet per coordinator, each showing only their own interns.

## Frontend UI conventions

Applies to the Vue SPA in `web/`. These describe what the code already does — follow them rather than inventing a parallel style.

- **Card chrome**: `rounded-xl bg-white p-6 shadow-sm ring-1 ring-slate-200/70` on every card. Tinted stat cards swap the white fill for a `-50/50` wash of their accent (`bg-blue-50/50`, `bg-emerald-50/50`, `bg-amber-50/50`, `bg-rose-50/50`) with `ring-1 ring-slate-200/60`.
- **Typography scale**: numerals `text-3xl font-semibold tracking-tight` (not extrabold); labels `text-xs font-medium uppercase tracking-wide text-slate-400`; section headings `text-sm font-semibold text-slate-900` with no left accent bar.
- **SVG progress convention**: always give the arc `pathLength="100"`, then `stroke-dasharray="100"` with `stroke-dashoffset="100 - percent"`. Never hand-compute a circumference — `pathLength` re-bases the geometry so the radius stops mattering. Gradient ids must be unique per instance (`gauge-ojt`, not `gauge`), since duplicate ids break rendering. Clamp every percentage to 0–100 before use, and render the neutral track alone when the denominator is 0 rather than faking a fill. A zero-length segment still paints a dot under `stroke-linecap="round"`, so omit the element entirely instead of drawing it at 0.
- **Dashboards render only fields the API already returns.** No invented counts, placeholder trends, or sample time-series. A number with no honest denominator gets no bar; a missing value renders `—`.
- **Tooltips**: `web/src/components/ui/TooltipWrap.vue` provides the visual (`label`, optional `placement` of `top`/`right`/`bottom`, default `top`). The tooltip element is `aria-hidden` decoration — the accessible name comes from an `aria-label` on the control itself, carrying the same string. Never add a native `title` alongside it; the browser would render a second tooltip on top. Shown on both `group-hover` and `group-focus-within`, so keyboard focus reveals it exactly like hover.
- **Sidebar collapse toggle** is anchored to the sidebar's right edge (`absolute right-0 translate-x-1/2` on the `<aside>`, which is `fixed` and therefore already the positioning context), not free-floating. It sits outside the scrolling `<nav>` so it never scrolls with the nav list.
- **Primary action buttons use the blue token** (`bg-blue-600` / `hover:bg-blue-700`); green is reserved for secondary and status actions, and black or dark-neutral primary buttons are not used.
- **Modals use a three-part flex shell, never `sticky` on the footer.** The overlay is `fixed inset-0 z-50 flex items-center justify-center p-4` and carries **no** `overflow`; the panel is `flex max-h-[90vh] w-full max-w-* flex-col overflow-hidden rounded-xl bg-white shadow-xl`; inside it sit exactly three siblings — a `shrink-0` header with `border-b`, a `flex-1 overflow-y-auto px-6 py-5` body that is the **only** scrolling element, and a `shrink-0` footer with `border-t bg-white px-6 py-4`. No element between the panel and the body may have its own overflow or height. A `sticky bottom-0` footer was tried and does not work here: when the overlay is the scroller, the panel grows past the viewport and the footer's containing block has no bottom edge on screen to pin against, so the bar drifts up over the content instead of staying put.
- **Render a date by slicing the string, never by parsing it.** Take the leading 10 characters (`value.slice(0, 10)`) for anything shown as a date. Almost every date the API returns is either a `date`-cast column Laravel serialises at midnight UTC (`"2026-05-29T00:00:00.000000Z"`) or a bare unmarked `"2026-07-29 21:37:00"` — and `new Date()` on either can land a day earlier once `APP_TIMEZONE` is `Asia/Manila`, which is what deployments set. Slicing cannot drift. Where the time still matters, keep the untouched original in a `TooltipWrap` beside the sliced value. A wall-clock time (`"21:00:00"`) is likewise formatted by splitting on `:` — it has no date, so there is no instant for a `Date` to represent. Only a genuine instant carrying a timezone marker may be parsed.
- **Derive a journal field's label from its key — never hardcode a map.** `journal_entries.content` is a JSON object keyed by whatever the coordinator's `journal_templates.sections` defines, so the keys differ per program and the API returns no label alongside them. Humanise the key instead (split on `_`, capitalise each word: `task_performed` → `Task Performed`), which stays correct for a template nobody anticipated; a hardcoded lookup silently falls back to raw snake_case the moment a coordinator adds a section. Render each as a label above its value, and skip fields whose value is blank rather than printing an empty label.
- **A stat card links to a filtered page only if that page actually reads the query param.** Several list pages hold their filter in a local `ref` and never consult `route.query`, so a `?status=…` link navigates without filtering and silently lies about where it is taking you. Check the destination page first; if it does not read the param, link to the plain page.
- **A table's actions cell is one right-aligned row of buttons at a fixed column width.** `flex items-center justify-end gap-2 whitespace-nowrap`, buttons `px-3 py-1.5 text-sm`, the neutral action a bordered outline button and the destructive one red text-only. The width belongs in a `<colgroup>` enforced by `table-fixed` — without `table-fixed` a browser treats col widths as hints and a long name can still squeeze the cell into wrapping onto two lines.

#### Dashboard structure

All four dashboards (student, coordinator, supervisor, admin) follow one order. A role skips a section only when it has no real data for it.

1. **Scope/status notices** — role-specific, one compact row each (`px-4 py-3`), longer explanation moved into a `TooltipWrap` on an info icon rather than a paragraph.
2. **Hero card** — `rounded-xl bg-white p-6 shadow-sm ring-1 ring-slate-200/70` holding an `h-14 w-14` initials avatar on `bg-blue-50`, `Hello, {first name}` in `text-xl font-semibold tracking-tight`, a muted subtitle of the role's most relevant context, and the page's single blue CTA as a `rounded-full` `RouterLink` with a right-arrow. The CTA target is the role's primary sidebar route, copied from the layout's `navItems` rather than retyped. A meta grid is rendered **only** where the endpoint returns fields worth showing — today that is the student alone, and the other three heroes correctly have none.
3. **Stat row** — `grid gap-4 sm:grid-cols-2 xl:grid-cols-4`, cards `flex h-full flex-col rounded-xl p-6 ring-1 ring-slate-200/60` with a `-50/40` tint, an `h-9 w-9` **white** icon tile carrying `ring-1 ring-slate-200/70` and a coloured glyph, the label beside the tile, the numeral `text-3xl font-semibold tracking-tight`, and a caption under. Accent order where the meaning matches: **blue** neutral, **emerald** good, **amber** waiting, **rose** needs attention. Only those four hues.
4. **Panels row** — under a `text-xs font-medium uppercase tracking-wide text-slate-400` section heading with `mb-3`; the grid is `items-stretch` and each panel `flex h-full flex-col` so a row is equal height. Every panel heading carries a one-line muted subtitle describing what it shows, written from the real data.
5. **Detail list** — activity feed, queue, or table.

- **Exactly one filled blue button per dashboard: the hero CTA.** Everything else is an outline button, a text link, or a card that happens to be a link. A second filled blue button means the page no longer has a primary action.
- **Amber means one thing: the single most actionable item.** At most one amber *notice* per page; any second notice drops to neutral slate (`bg-slate-50` + `ring-slate-200/70`), and the actionable notice sits above the informational one. Amber as a stat-card accent or a data-series colour is separate from this and unaffected.
- Page rhythm is `space-y-6`.
