How to read this document

Text shown in red with a strikethrough is the wording in the current documentation that is being replaced or corrected.

Text shown in green is the corrected or newly added wording.

Each entry cites where it appears in the source PDF and why it changed. Every correction below was checked against the actual implementation, not assumed.

This redline covers factual drift between the written documentation and the system as built. The largest recurring issues are the weekly bundling day (documented as Sunday, implemented as Monday), the reminder schedule (documented as a fixed 9:00 PM coordinator setting, implemented as an hourly job driven by each student's own preference), the coordinator's permissions (documented as read-only, actually a full management role), and the local development stack (documented as XAMPP, actually Laragon with Laravel's built-in server).

Deliberately left unchanged: the mobile application

Every statement about the React Native mobile application and mobile push notifications is retained exactly as written in the source document. The mobile component has not been implemented yet, so no revision is proposed for it in this pass and the existing wording stands as the project's stated intent.

Where a sentence mentions mobile alongside something that genuinely did need correcting — the reminder schedule, for example — only the non-mobile portion is marked, and the mobile clause is left untouched.

Chapter I — §1.2 Purpose and Description

Page 3 — automated weekly bundling
WasInternTrack features weekly automated bundling of daily entries into a weekly log on Sundays…
NowInternTrack features weekly automated bundling of daily entries into a weekly log every Monday at 00:00, compiling the full Monday–Sunday week that has just ended…
Reason — routes/console.php schedules RunWeeklyBundling with weeklyOn(1, '00:00'); day 1 is Monday. The job previously ran on Saturday, which was corrected because stamping a Weekly Log locks every daily entry in that week — a Saturday run locked the week before a Saturday shift had even started, leaving a rostered intern unable to write that day's entry.
Page 2 — student notifications
WasStudents are notified by email, on the web, and via mobile applications about overdue and missing journal entries.
NowStudents are notified by email, where the address has been verified, on the web, and via mobile applications about overdue and missing journal entries.
Reason — Reminder email is sent only when email is present and email_verified_at is set; a student without a verified address receives the in-app notification instead. Because most students are created by coordinators without an email address, the in-app bell is the usual delivery path in practice. The web and mobile channels are left as written.
Page 2 — supervisor scope
WasCompany supervisors also have another window to view and comment on student's weekly journals from other batches before approving or sending them back.
NowCompany supervisors also have another window to view and comment on the weekly journals of the interns hosted at their own company before approving or sending them back.
Reason — Supervisor scope is by company, not batch. ScopesSupervisorWork resolves the companies the signed-in supervisor is attached to and returns every enrolment at those companies, which is what lets one shared company login see that company's full roster.

Chapter I — §1.3 Objectives

Page 4 — weekly compilation objective
WasTo implement a process that compiles daily entries into a single weekly file each Sunday for supervisor approval…
NowTo implement a process that compiles daily entries into a single weekly file every Monday at 00:00, covering the Monday–Sunday week just ended, for supervisor approval…
Reason — Same schedule correction as above. A week is only treated as complete once its Sunday has passed, so the compilation necessarily runs on the following Monday.
Page 4 — reminder objective
WasTo include an auto-email reminder script that emails students about missing or late daily logs at 9:00 PM, customized by coordinators for different batches of students, and sends these reminders to the mobile app as push notifications.
NowTo include an auto-email reminder script that emails students about missing or late daily logs at a time each student sets for themselves — the service runs hourly and notifies a student in their chosen hour, falling back to their batch's schedule and then to a 9:00 PM default, and sends these reminders to the mobile app as push notifications.
Reason — journal:send-missing-entry-reminders is scheduled ->hourly(); the command itself decides whose hour it currently is. Reminder preferences are stored per student (reminder_days, reminder_time, reminder_enabled on student_profiles) and are the student's own setting, not a coordinator's. The batch's daily_reminder_time is only a fallback. The mobile push clause is left as written.
Page 3 — review and approval tiers
Was…utilize the OJT journal's built-in review and approval process that consists of many tiers, such as immediate supervisors and upper management coordinators…
Now…utilize the OJT journal's built-in review and approval process in which the company supervisor is the sole approving authority — approving a weekly journal or returning it with a required comment — while academic coordinators observe the outcome in a read-only capacity…
Reason — There is exactly one approval tier. CoordinatorWeeklyJournalController exposes no approve, return, or edit action anywhere; review verdicts belong to supervisors only. Describing coordinators as an approval tier overstates the workflow.
Page 5 — Weekly Activity Log objective
WasTo implement Weekly Activity Log functionality for students to record and report highlights of their weekly activities, as well as automatically include approved Journal Entry input for the Student SIPP report available to coordinators.
NowTo automatically include approved Journal Entry input for the Student SIPP report available to coordinators. (The separate student-facing Weekly Activity Log form was withdrawn from the interface; its function is served by the supervisor-reviewed Weekly Journal.)
Reason — The "Weekly Activity Log (SIPP)" section was removed from the student interface because no coordinator, supervisor, or administrator ever viewed it and it duplicated the Weekly Narrative. The database tables, controller, routes, and PDF template were deliberately retained so the capability is recoverable, but it is no longer a user-facing feature and should not be documented as one.
Page 5 — responsive delivery objective (wording)
WasTo deliver a responsive web application that operated effectively across desktop and mobile browsers…
NowTo deliver a responsive web application that operates effectively across desktop and mobile browsers…
Reason — Tense agreement with the surrounding objectives. This objective is now met: all four role interfaces use an off-canvas navigation drawer below the medium breakpoint, and all 28 role pages were verified at 320 px, 375 px, and 768 px with no horizontal overflow.

Chapter I — §1.4 Scope and Limitations

Page 6 — Weekly Processing
WasWeekly Processing: The system automatically collects daily logs into a weekly format every Sunday evening, including only entries supplied inside the active batch schedule.
NowWeekly Processing: The system automatically collects daily logs into a weekly format every Monday at 00:00 for the week just ended, including only submitted entries from students with an active enrolment.
Reason — Schedule correction, plus a precision point: bundling compiles only submitted daily entries. Days without a submitted entry are skipped silently rather than filled with a placeholder, and an already-submitted Weekly Log is never overwritten.
Page 6 — Coordinator Tools
WasCoordinator Tools: A portal for administering programs and tracking multiple student groups. Includes read-only access to all records approved by supervisors.
NowCoordinator Tools: A portal for administering programs and tracking multiple student groups. Coordinators create student and supervisor accounts, manage batches and their rosters, maintain partner companies, author journal templates, accept or reject Student Information Sheets (acceptance is what enrols a student), and curate the SIPP, HTE, and Group Information Sheet reports. Their access is read-only only with respect to journal content itself.
Reason — "Read-only" materially understates the role. There are twelve coordinator controllers with write capability. Most significantly, accepting a Student Information Sheet is the action that creates the enrolment record — the single gateway through which every student enters a batch.
Page 7 — Notification Engine
WasNotification Engine: Send automatic email and mobile push notifications to students with open journals who have not submitted partially complete, based on reading batch parameters.
NowNotification Engine: Send automatic email and mobile push notifications to students who have not submitted a daily journal on a day they were expected to work. Email is sent where the student's address has been verified, and an in-app notification is always recorded. Timing follows each student's own reminder preference, falling back to their batch's schedule.
Reason — The original sentence is grammatically incomplete ("who have not submitted partially complete") and attributes the timing to batch parameters alone. Corrected for readability and to reflect the per-student reminder preference plus the email-verification condition. The email and mobile push channels are left as written.
Page 7 — Weekly Activity Log scope item
WasWeekly Activity Log: Students can record and submit their weekly activities. Approved daily logs will be automatically reflected in their SIPP report, which coordinators can view.
NowWeekly Journal: Students write a weekly narrative, which the company supervisor approves or returns with a comment. SIPP-flagged journal fields feed the coordinator's Annual SIPP Report.
Reason — Reflects the removal of the standalone Weekly Activity Log form and names the feature that actually performs this role.
Page 8 — Connectivity Requirement (limitation)
WasConnectivity Requirement: The platform needs a stable internet connection… However, Offline drafts and local saving are features now available but require internet connection to use, so users should make sure they are connected to the internet before using the platform.
NowConnectivity Requirement: The platform needs an internet connection to load data, save work, and submit reports. Work typed into a form is preserved in the browser for the duration of the tab, so refreshing the page — or recovering from a browser crash — does not discard unsaved input. This is a convenience only: the data is not submitted to the server until the user saves, and no feature operates fully offline.
Reason — The original sentence contradicts itself, describing offline drafts as available while requiring an internet connection to use them. It has been rewritten to state what the system genuinely does: form input is mirrored into per-tab browser storage and restored after a refresh. Per-tab storage was chosen deliberately over persistent storage because the system is used on shared college laboratory machines, and a half-completed Student Information Sheet containing personal and guardian details must not remain readable to the next user of that browser. Passwords are explicitly excluded from this mechanism.

Chapter III — §3.1 Architecture Design

Page 13 — coordinator capability
WasAcademic coordinators can look at what many students are doing, but they cannot change anything.
NowAcademic coordinators can look at what many students are doing across their department, and they administer the structures those students work within — accounts, batches, rosters, partner companies, journal templates, intake approval, and the SIPP compliance reports. What they cannot alter is journal content itself or a supervisor's review decision.
Reason — Same correction as the Coordinator Tools scope entry; this sentence is the strongest statement of the inaccuracy and is the one most likely to be quoted during the defence.
Page 14 — backend responsibilities
WasThe part that makes it work includes rules such as creating weekly bundles, sending emails every Sunday, and generating PDF reports.
NowThe part that makes it work includes rules such as compiling weekly bundles each Monday, running the hourly reminder service, purging expired archived roster records nightly, and generating PDF reports.
Reason — Corrects the schedule and names the third scheduled task the documentation omits: roster:purge-archived runs daily at 02:00 and permanently removes archived roster records older than thirty days.

Chapter III — §3.2 Details of Technology Used

Page 16 — XAMPP
WasXAMPP — a local server environment used throughout the development and testing stages of InternTrack. XAMPP provides a locally-hosted Apache web server, MySQL database, and PHP interpreter.
NowLaragon and the Laravel development server — the local environment used during development and testing. Laragon supplies the MySQL service, while the application itself is served by Laravel's built-in development server (php artisan serve) alongside the Vite development server for the Vue front end.
Reason — XAMPP is not the stack in use. MySQL is provided by Laragon, and the application runs under php artisan serve with Vite proxying API requests, which is what makes the front end and API same-origin during development.
Page 16 — new entry to add after the local environment
AddDeployment platform — the production build is split across three free-tier services: the Vue front end is hosted on Vercel, the Laravel API runs as a Docker container on Render, and the MySQL database is hosted on Aiven. The front end proxies API requests to the backend so that both appear to the browser as a single origin, which keeps authentication working without third-party cookies.
Reason — The document describes only the local environment and never states how the system is deployed, which is a question the panel is likely to ask. The full operational procedure is documented separately in docs/DEPLOYMENT.md.
Page 14 — Laravel
WasLaravel — a PHP web application framework… including automatic journal bundling on Sundays, the email reminder engine, the four-tier review and approval workflow…
NowLaravel 13 (PHP 8.3) — a PHP web application framework… including automatic journal bundling each Monday, the hourly reminder engine, the supervisor review and approval workflow…
Reason — Adds the version actually in use and applies the schedule and workflow corrections. "Four-tier" conflates the four user roles with the review workflow, which has one approving tier.
Page 14 — Vue
WasVue — Vue.js is the JavaScript framework we used to build InternTrack's web view.
NowVue 3 with TypeScript — the front-end framework used to build InternTrack's web interface, built with Vite and using Pinia for application state and Vue Router for navigation. TypeScript is used throughout the front end so that data exchanged with the API is type-checked at build time.
Reason — The front end is TypeScript, not plain JavaScript, and the supporting libraries (Vite, Pinia, Vue Router) are unstated. These are reasonable things for a panel to ask about.
Page 15 — Tailwind CSS
WasTailwind CSS — is a utility-first framework…
NowTailwind CSS v4 — is a utility-first framework…
Reason — Version 4 differs enough from version 3 in configuration and syntax that the major version is worth stating.
Page 15 — new entry to add
AddAuthentication — sign-in is username and password based, using Laravel Sanctum's cookie and session authentication for the web application. Google sign-in is additionally available in a strictly link-only capacity: it never creates an account and only signs in an existing account whose email address Google itself has verified. The same mechanism is what verifies a student's email address so that reminder email may be sent to them.
Reason — Authentication is not described anywhere in the technology chapter, yet it is central to the system. It is also worth stating explicitly that self-registration does not exist — every account is created by staff — since that is a deliberate security decision rather than an omission.
